반드시 완전히 구별되는 세 개의 자료구조를 구현할 필요는 없다. 관련된 자원들을 하나의 통합된 자료구조로 전체적으로 또는 부분적으로 합치는 것이 편리할 수도 있다.

각 자료구조에 대해, 각 원소가 어떤 정보를 포함해야 하는지 결정해야 한다. 또한 자료구조의 범위를 로컬(프로세스별)로 할지, 글로벌(전체 시스템에 적용)로 할지, 그리고 그 범위 안에서 몇 개의 인스턴스가 필요한지도 결정해야 한다.

설계를 단순하게 하기 위해, 이러한 자료구조들을 non-pageable memory(예: `calloc` 또는 `malloc`으로 할당한 메모리)에 저장해도 된다. 이렇게 하면 그들 사이의 포인터들이 항상 유효하다고 확신할 수 있다.

## Choices of implementation (Performance perspective)

구현 선택지로는 배열, 리스트, 비트맵, 해시 테이블 등이 있다. 배열은 종종 가장 단순한 접근이지만, 드문드문 채워진 배열은 메모리를 낭비한다. 리스트 역시 단순하지만, 특정 위치를 찾기 위해 긴 리스트를 순회하는 것은 시간을 낭비한다. 배열과 리스트 모두 크기 조절이 가능하지만, 리스트는 중간에서의 삽입과 삭제를 더 효율적으로 지원한다.

Pintos는 `lib/kernel/bitmap.c`와 `include/lib/kernel/bitmap.h`에 비트맵 자료구조를 포함하고 있다. 비트맵은 각 비트가 참 또는 거짓일 수 있는 비트 배열이다. 비트맵은 보통 동일한 자원 집합의 사용 여부를 추적하는 데 사용된다. 자원 `n`이 사용 중이면 비트맵의 `n`번째 비트는 참이다. Pintos 비트맵은 크기가 고정되어 있지만, 원한다면 크기 조절을 지원하도록 확장할 수도 있다.

Pintos는 또한 해시 테이블 자료구조도 포함하고 있다(See Hash Table). Pintos 해시 테이블은 다양한 테이블 크기 범위에서 삽입과 삭제를 효율적으로 지원한다.

더 복잡한 자료구조가 더 나은 성능이나 다른 이점을 줄 수는 있지만, 구현을 불필요하게 복잡하게 만들 수도 있다. 따라서 우리는 설계의 일부로 고급 자료구조(예: balanced binary tree)를 구현하는 것을 권장하지 않는다.

## Managing the Supplemental Page Table

Supplemental page table은 각 페이지에 대한 추가 데이터를 페이지 테이블에 보완하여 제공한다. 페이지 테이블 형식이 가지는 한계 때문에 이 구조가 필요하다. 이런 자료구조 자체도 종종 "page table"이라고 불리지만, 혼동을 줄이기 위해 우리는 "supplemental"이라는 단어를 덧붙인다.

Supplemental page table은 적어도 두 가지 목적에 사용된다. 가장 중요한 목적은, 페이지 폴트가 발생했을 때 커널이 supplemental page table에서 fault가 발생한 가상 페이지를 찾아 그곳에 어떤 데이터가 있어야 하는지 알아내는 것이다. 두 번째 목적은 프로세스가 종료될 때 커널이 어떤 자원을 해제해야 하는지 판단하기 위해 supplemental page table을 참조하는 것이다.

### Organization of Supplemental Page Table

Supplemental page table은 원하는 대로 구성할 수 있다. 그 구성에는 적어도 두 가지 기본적인 접근 방식이 있다. 하나는 세그먼트 단위로 구성하는 방식이고, 다른 하나는 페이지 단위로 구성하는 방식이다. 여기서 세그먼트는 연속된 페이지들의 그룹, 즉 실행 파일이나 memory-mapped file을 포함하는 메모리 영역을 의미한다.

선택적으로, 페이지 테이블 자체를 사용하여 supplemental page table의 멤버들을 추적할 수도 있다. 그러려면 `threads/mmu.c`에 있는 Pintos 페이지 테이블 구현을 수정해야 한다. 이 접근은 고급 학생들에게만 권장한다.

### Handling page fault

Supplemental page table의 가장 중요한 사용자는 page fault handler이다. 프로젝트 2에서는 페이지 폴트가 항상 커널 또는 사용자 프로그램의 버그를 의미했다. 프로젝트 3에서는 더 이상 그렇지 않다. 이제 페이지 폴트는 단지 그 페이지를 파일이나 스왑 슬롯으로부터 가져와야 한다는 뜻일 수 있다. 이러한 경우들을 처리하기 위해 더 정교한 page fault handler를 구현해야 한다. `userprog/exception.c`의 `page_fault()`는 `vm/vm.c`의 `vm_try_handle_fault()`인 여러분의 page fault handler를 호출한다. 여러분의 page fault handler는 대략 다음과 같은 일을 해야 한다.

1. fault가 발생한 페이지를 supplemental page table에서 찾는다. 메모리 참조가 유효하다면, supplemental page table 엔트리를 사용해 그 페이지에 들어가야 할 데이터의 위치를 찾는다. 그 데이터는 파일 시스템에 있을 수도 있고, 스왑 슬롯에 있을 수도 있고, 단순히 모든 바이트가 0인 페이지일 수도 있다. 공유(즉, Copy-on-Write)를 구현했다면, 페이지의 데이터가 이미 어떤 페이지 프레임 안에는 있지만 페이지 테이블에는 아직 없을 수도 있다. supplemental page table이 사용자 프로세스가 접근한 주소에 어떤 데이터도 기대하면 안 된다고 나타내거나, 그 페이지가 커널 가상 메모리 안에 있거나, 읽기 전용 페이지에 대한 쓰기 시도라면, 그 접근은 유효하지 않다. 어떤 유효하지 않은 접근이라도 프로세스를 종료시키며, 그에 따라 해당 프로세스의 모든 자원이 해제된다.
2. 페이지를 저장할 프레임을 얻는다. 공유를 구현했다면, 필요한 데이터가 이미 프레임 안에 있을 수 있으며, 그 경우에는 그 프레임을 찾을 수 있어야 한다.
3. 파일 시스템이나 스왑에서 읽어오거나, 0으로 채우는 등의 방식으로 데이터를 프레임에 가져온다. 공유를 구현했다면, 필요한 페이지가 이미 프레임 안에 있을 수 있고, 이 경우 이 단계에서는 아무 작업도 필요 없다.
4. fault가 발생한 가상 주소에 대한 페이지 테이블 엔트리가 물리 페이지를 가리키도록 설정한다. 이를 위해 `threads/mmu.c`의 함수들을 사용할 수 있다.

## Managing the Frame Table

Frame table은 각 프레임마다 하나의 엔트리를 가진다. frame table의 각 엔트리는 현재 그 프레임을 차지하고 있는 페이지가 있다면 그 페이지를 가리키는 포인터와, 여러분이 선택한 다른 데이터들을 포함한다. frame table은 free frame이 없을 때 어떤 페이지를 내보낼지 선택함으로써, Pintos가 eviction 정책을 효율적으로 구현할 수 있게 해 준다.

사용자 페이지에 사용되는 프레임은 반드시 `palloc_get_page(PAL_USER)`를 호출하여 "user pool"에서 얻어야 한다. "kernel pool"에서 할당해 버리면 어떤 테스트 케이스들이 예상치 못하게 실패할 수 있으므로, 이를 피하기 위해 반드시 `PAL_USER`를 사용해야 한다. frame table 구현의 일부로 `palloc.c`를 수정하더라도, 두 풀의 구분은 반드시 유지해야 한다.

frame table에서 가장 중요한 연산은 사용되지 않은 프레임을 얻는 것이다. 프레임이 비어 있다면 이는 쉽다. 빈 프레임이 하나도 없다면, 어떤 페이지를 그 프레임에서 내보내어 프레임을 비워야 한다.

어떤 프레임도 스왑 슬롯을 할당하지 않고는 eviction할 수 없는데 스왑이 가득 찼다면, 커널을 panic시켜라. 실제 운영체제는 이런 상황을 복구하거나 예방하기 위해 매우 다양한 정책을 사용하지만, 그것들은 이 프로젝트의 범위를 벗어난다.

eviction 과정은 대략 다음 단계들로 이루어진다.

1. 여러분의 페이지 교체 알고리즘을 사용해 내보낼 프레임을 선택한다. 아래에서 설명하는 페이지 테이블의 "accessed" 비트와 "dirty" 비트가 유용할 것이다.
2. 그 프레임을 참조하는 모든 페이지 테이블에서 프레임에 대한 참조를 제거한다. 공유를 구현하지 않았다면, 한 시점에 하나의 프레임은 오직 하나의 페이지만 참조해야 한다.
3. 필요하다면, 그 페이지를 파일 시스템이나 스왑에 기록한다. 그러면 비워진 프레임은 다른 페이지를 저장하는 데 사용할 수 있다.

## Accessed and Dirty Bits

x86-64 하드웨어는 페이지 교체 알고리즘을 구현하는 데 도움을 주기 위해, 각 페이지의 페이지 테이블 엔트리(PTE)에 두 개의 비트를 제공한다. 페이지에 대해 읽기 또는 쓰기가 일어나면 CPU는 그 페이지의 PTE에서 accessed bit를 1로 설정하고, 쓰기가 일어나면 dirty bit를 1로 설정한다. CPU는 이 비트들을 절대 다시 0으로 되돌리지 않지만, 운영체제는 그렇게 할 수 있다.

여러분은 alias, 즉 하나의 프레임을 참조하는 두 개 이상의 페이지를 반드시 고려해야 한다. alias된 프레임에 접근하면 accessed bit와 dirty bit는 오직 하나의 페이지 테이블 엔트리(실제로 접근에 사용된 페이지의 엔트리)에서만 갱신된다. 다른 alias들의 accessed bit와 dirty bit는 갱신되지 않는다.

Pintos에서는 모든 사용자 가상 페이지가 그에 대응되는 커널 가상 페이지와 alias 관계를 가진다. 여러분은 이 alias들을 어떤 방식으로든 관리해야 한다. 예를 들어, 코드에서 두 주소 모두에 대해 accessed bit와 dirty bit를 확인하고 갱신할 수 있다. 또는 커널이 사용자 데이터를 오직 사용자 가상 주소를 통해서만 접근하게 함으로써 이 문제를 피할 수도 있다.

다른 alias는 공유를 구현했거나 코드에 버그가 있는 경우에만 발생해야 한다.

accessed bit와 dirty bit를 다루는 함수들에 대한 자세한 내용은 `Section Page Table Accessed and Dirty Bits`를 참고하라.

## Managing the Swap Table

Swap table은 사용 중인 스왑 슬롯과 비어 있는 스왑 슬롯을 추적한다. 이 자료구조는 프레임에서 스왑 파티션으로 페이지를 내보내기 위해 비어 있는 스왑 슬롯 하나를 선택할 수 있어야 한다. 또한 스왑된 페이지가 다시 읽혀 들어오거나, 스왑된 페이지를 가진 프로세스가 종료될 때 해당 스왑 슬롯을 해제할 수 있어야 한다.

`vm/build` 디렉터리에서 `pintos-mkdisk swap.dsk --swap-size=n` 명령을 사용하여 `n`MB 크기의 swap partition을 가진 `swap.dsk`라는 디스크를 만들 수 있다. 이후에는 `pintos`를 실행할 때 `swap.dsk`가 자동으로 추가 디스크로 연결된다. 또는 한 번의 실행에 대해서만 `--swap-size=n`을 사용하여 임시 `n`MB 스왑 디스크를 사용하도록 할 수도 있다.

스왑 슬롯은 lazy하게 할당되어야 한다. 즉, eviction에 의해 실제로 필요해질 때에만 할당해야 한다. 실행 파일로부터 데이터 페이지를 읽어와 프로세스 시작 시점에 즉시 스왑에 써 넣는 것은 lazy하지 않다. 또한 특정 페이지를 저장하기 위해 스왑 슬롯을 미리 예약해서도 안 된다.

스왑 슬롯의 내용이 프레임으로 다시 읽혀 들어오면 그 스왑 슬롯을 해제하라.

## Managing Memory Mapped Files

파일 시스템은 가장 일반적으로 `read`와 `write` 시스템 콜을 통해 접근된다. 두 번째 인터페이스는 `mmap` 시스템 콜을 사용해 파일을 가상 페이지들에 "매핑"하는 것이다. 그러면 프로그램은 파일 데이터에 직접 메모리 명령으로 접근할 수 있다. 예를 들어 파일 `foo`의 길이가 `0x1000`바이트(4kB, 즉 한 페이지)라고 하자. `foo`가 메모리의 `0x5000` 주소부터 매핑되어 있다면, `0x5000 ... 0x5fff` 위치에 대한 메모리 접근은 `foo`의 해당 바이트들에 접근하게 된다.

다음은 `mmap`을 사용해 파일을 콘솔에 출력하는 프로그램이다. 이 프로그램은 명령줄에 지정된 파일을 열고, 그것을 가상 주소 `0x10000000`에 매핑한 뒤, 매핑된 데이터를 콘솔(fd 1)에 쓰고, 마지막으로 매핑을 해제한다.

```c
#include <stdio.h>
#include <syscall.h>
int main (int argc UNUSED, char *argv[])
{
  void *data = (void *) 0x10000000;                 /* Address at which to map. */
  int fd = open (argv[1]);                          /* Open file. */
  void *map = mmap (data, filesize (fd), 0, fd, 0); /* Map file. */
  write (1, data, filesize (fd));                   /* Write file to console. */
  munmap (map);                                     /* Unmap file (optional). */
  return 0;
}
```

여러분의 제출물은 memory mapped file이 사용하는 메모리가 무엇인지 추적할 수 있어야 한다. 이는 매핑된 영역에서 발생하는 페이지 폴트를 올바르게 처리하고, 매핑된 파일들이 프로세스 내부의 다른 어떤 세그먼트와도 겹치지 않도록 보장하기 위해 필요하다.
